# Inori 迭代设计与路线图

## 本轮目标：0.3 可信评审

本轮优先解决三个使用问题：本次到底审了哪些文件、模型是否有效完成评审、发现是否完整发布。继续保持单包 GitHub Action、自带密钥、任意 OpenAI 兼容端点的定位，不引入外部服务或数据库。

“0.3”是迭代目标，不表示已发布版本。版本号、CHANGELOG 和 manifest 仍由 release-please 在后续发布流程中生成，本轮不手工改版本号，也不直接打标签或发布。

## 本轮实现

| 范围 | 行为与目的 |
|---|---|
| 配置可信来源 | 通过 GitHub Contents API 从事件的固定 base SHA 读取 `.github/inori.yml` 或 `.yaml`，不读取 checkout 工作区；读取或校验失败停止 |
| 快照一致性 | 在读取前后及发布前核对 PR head/base SHA，发现变化停止发布 |
| 有效结果判定 | 严格校验 JSON 结构、字段类型与模型完成状态；失败不能表示“没有问题” |
| 可见覆盖范围 | 对完整文件执行硬字符预算，省略放不下的文件并继续考虑后续文件；披露预算、无 patch、API 文件缺口 |
| 发布完整性 | 无效行号进入汇总；inline 发布失败的发现完整补入汇总；正文不能容纳全部内容时失败，保留旧意见 |
| 历史保护 | 每轮新增关联提交的汇总；只有覆盖完整且发布成功才按作者身份和发布前评论快照清理旧 inline；有人回复的讨论保留 |
| 运行结果 | 输出 `status`、`head_sha`、`findings_count`、`reviewed_files`、`omitted_files`、`reason`，并写入 Actions 运行摘要 |
| 凭据选择 | 使用显式 key、所选 provider 专属环境变量或通用环境变量；不回退到其他 provider 的默认 key |
| 发布门禁 | 验证实际候选提交 SHA 后才授权 release-please 发布，并校验移动 major 标签的目标提交 |

`completed` 表示评审流程完整完成，不表示零发现。`partial` 表示覆盖有缺口或 inline 发布降级；如果没有可用 diff，也可能没有发布任何评论。`skipped` 表示规则跳过，`stale` 表示快照变化，`failed` 表示执行失败。`reviewed_files` 在获得合法模型结果后才计数；发布失败时仍可大于零。GitHub Actions 输出值使用字符串表示数量。

### 模块边界

- `src/index.ts`：启动入口。
- `src/run.ts`：编排可信配置、跳过规则、快照检查、模型调用、发布和最终运行状态。
- `src/config/`：Action 输入、仓库配置结构校验与优先级合并，不读取 PR 工作区。
- `src/core/`：diff、覆盖统计文案、prompt、结果解析、正文生成与跳过规则；纯逻辑不依赖 `@actions/core`。
- `src/github/`：固定 base 配置读取、PR 快照与分页、发布、历史归属识别和清理。
- `src/llm/`：provider 解析、凭据选择、HTTP 超时与有限重试、传输层响应校验。
- `.github/workflows/verify.yml`：供 CI 与发布流程复用的源码、测试、构建和 dist 一致性验证。
- `scripts/release-gate.mjs`：发布候选快照、验证授权和 major 标签对齐。

保留直接函数调用和现有模块，不建立通用工作流引擎、插件系统或多层状态机。运行状态由编排层汇总；纯函数返回数据或抛明确错误。

### 设计取舍

**先保证结果可解释，再扩大评审范围。** 当前仍是一轮模型请求，不对文件或 hunk 分片。字符预算不等于 token 预算；模型上下文不足仍可能失败。某个大文件放不下时保留后续小文件的评审机会，但会明确标注部分覆盖，不能把模型结论外推到未评审文件。

**不把缺少 patch 当成无问题。** GitHub 的文件列表最多返回 3000 个文件，部分文件也可能没有 patch。通过 PR 的文件总数和实际列表长度记录 API 缺口；不会自行下载或执行 PR 代码补齐上下文。

**失败保旧，汇总留痕。** 旧汇总保持原样，每轮新增汇总会增加历史长度，但避免把旧提交的 review 改写成新提交的结论。覆盖不完整时保留全部旧 inline，避免删除本轮未审文件的发现。发布不是事务：网络失败可能留下部分新评论，运行会标记失败，旧评论不因而删除。

**快照检查不宣称消除所有竞态。** 多次核对 head/base 可发现生成期间的更新；最后一次检查与 GitHub 写入之间仍存在时间窗口。工作流保留按 PR 取消旧运行的 concurrency 设置，评论绑定本轮 SHA。

**模型仍是辅助评审。** Prompt 已包含“不可信 diff”说明，字段校验也只能证明输出结构有效，不能证明每条判断正确。本轮不自动 APPROVE、REQUEST_CHANGES，也不据模型严重度阻断合并。

### 兼容变化

1. 无需 `actions/checkout`，但通过 API 读取可信配置仍需 `contents: read`。PR 中修改配置要在合并后、后续 base SHA 包含修改时才生效。
2. 以前被忽略或回退的非法 YAML、字段类型、枚举、预算和不合法模型结果现在失败。空文件、仅注释文件和确实不存在的配置仍允许默认值。
3. `max_diff_chars` 是完整文件块的硬预算；首个超大文件也会省略。`max_body_chars` 包含完整汇总、覆盖说明及标记，超限失败，不截断意见。
4. 汇总不再原地更新；`replace`、`resolve` 只在完整成功后处理符合条件的旧 inline。部分覆盖、inline 降级或执行失败保留历史。
5. 未识别 provider 的自定义端点不能擅用默认 DeepSeek 环境密钥；需提供显式 key 或 `LLM_API_KEY`。已指定 provider 的代理端点仍可使用该 provider 专属环境变量。
6. 普通 fork PR 的 secrets 和写权限限制没有改变。本轮没有实现特权 fork 评审，也没有切换为 `pull_request_target`。

## CI/CD 的本轮变化与剩余边界

普通 CI 调用 `verify.yml` 执行 lint、typecheck、test、build 和 dist 一致性验证。Node 保持 24，pnpm 固定精确版本，外部 Actions 固定完整 commit SHA。

发布与历史标签恢复分别验证，互不依赖：

- `plan → verify → publish`：只收集已合并到 main、带 pending/verified 标签的 release PR，以其不可变 `merge_commit_sha` 组成候选验证矩阵。已有 verified 标签也重新验证。整个矩阵通过后复核候选、添加 `autorelease: verified`，再由专用配置允许 release-please 发布；任一候选失败则本批不发布、不加标签。并发新合并的 pending 候选留待下轮。
- `recovery-plan → verify-recovery → recover`：独立读取每个 major 的最新正式 Release，仅当 major 标签缺失或未指向该 Release 时才验证对应历史 SHA，再执行标签恢复。无需恢复的历史版本不重建。历史查询、规划或验证失败不会阻止新候选发布。
- `maintain`：独立维护 release PR，不依赖新版本发布或历史恢复成功。`release-please-config.json` 用于 PR 维护，`release-please-release-config.json` 用于验证后的实际发布。

各链路仅在 main 运行，写权限按 job 授予：`publish` 与 `maintain` 拥有内容和 PR 写权限，`recover` 仅有内容写权限；规划和验证只读。`publish`、`recover` 必须各自验证成功才执行；空矩阵直接跳过对应链路。

major 标签对齐不再依赖 `release_created`。发布和恢复各自只能推进本链路已验证的 SHA，遇到其他目标或并发新出现的 Release 就跳过并告警，留待后续验证，避免旧恢复覆盖新版本。更新已有标签还要求向前关系，回退或分叉会失败，不强制覆盖。手动重跑可恢复已存在 Release 的 major 标签；历史提交若无法在当前环境通过验证，只阻断相应恢复链路，需要修复或明确处理，不能直接绕过验证。

这些代码变化不等于远端仓库治理已经生效。仍需管理员设置 main 分支保护、必需检查、绕过权限，以及只允许 squash 和合并后删除分支。release PR 的独立检查仍受 token 与仓库 Actions 策略影响；本轮发布前验证候选 SHA，不替代合并前保护。

依赖审计目前仍为 advisory；尚未完成高危漏洞处置或定期审计自动化。Marketplace 发布也仍需人工完成相应平台操作。本轮不修改远端设置或自动发布版本。

## 下一阶段：大 PR 与可控成本

目标是增加可审覆盖率，同时让请求次数和费用有明确上限。

- 按完整文件优先分批；仅当单文件超限时研究按完整 hunk 分片，并为必要上下文预留预算。
- 总字符或 token 预算、最大请求数和有限并发共同约束成本；重试也计入预算。
- 每批结果分别记录成功、失败和覆盖，汇总时不把失败批次视为干净结果。
- 合并重复发现，保留证据位置；新增模型返回 token 用量与耗时统计，不猜测无法取得的费用。

验收以大文件、大量小文件、部分批次失败和限额耗尽场景为准；覆盖扩大必须能从 outputs 与汇总中验证。

## 再下一阶段：持续评审质量

目标是在重复 push 中减少噪声，同时保留尚未解决的问题。

- 以 base/head、配置、模型和 prompt 版本确定可复用结果范围，不只依赖文件名缓存。
- 建立发现指纹，区分同一缺陷、移动位置和新问题；人工回复与处置状态不可被自动覆盖。
- 先准备包含真实缺陷、误报、行号变化和提示注入样本的离线评测集，再引入增量策略与反馈。
- 记录人工采纳、误报反馈和重复率，用评测结果决定是否增加严重度过滤或可选门禁。

这些功能均属于后续设计，不是本轮已交付能力。

## 暂不扩展

暂不增加 provider 数量、自动修复提交、自动 approve、跨仓库知识平台或多代理评审。当前收益更高的是提升可靠性、覆盖透明度和评测质量；待这些基础成熟，再根据真实使用反馈决定扩展范围。
